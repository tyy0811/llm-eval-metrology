## 1. Scope, and what is deliberately not here

In scope: the five deliverables above, the README Status rewrite D3.3 left open, and the
`prose-check` and `report-check` targets of section 8, wired into `make check` and into CI as
explicit named steps.

Not in scope: `make reproduce` becoming real (T3.5), the card set rendering (T3.4), the cross-repo
handoff (T3.6).

**One additive reopening of T3.2's output, and only one.** PREREG section 2.1 registers the
headline as a three-part count: pairs distinguishable, pairs not distinguishable under a real
test, and pairs not distinguishable by tie arithmetic. Checked against the corpus: the
distinguishable count's genuine home is `primary.resolved_count` = 0 (the PREREG section 5
definition, observed Holm rejections), the real-test count's is
`secondary.non_tied_family.size` = 10, but the tie-forced count of 9 exists nowhere. The only
committed 9 is
`secondary.non_tied_family.gap_floor`, which is the secondary family's Holm floor, so prose citing
the tie count would pass membership by matching a semantically unrelated value, the exact
accidental-membership failure this design exists to prevent. `run.py` therefore gains a
`primary.headline` block, and `results.json` is regenerated. Nothing else in `run.py` changes; no
statistic is altered; the addition is recorded in DECISIONS. Beyond this, the reporting step reads
what T3.2 produced and recomputes nothing.

The schema and its formulas, exact, because the first draft of this block said distinguishable
equals `separable_count` and that is the D2.6 conflation over again, masked by both counts being
zero on this data. PREREG section 5 defines distinguishable as "Holm-adjusted p below 0.05",
which is the **observed** rejection, `resolved_count`. Separability is the best-case bound D2.7
built precisely so the two would stay distinct:

```json
"headline": {
  "distinguishable_count": 0,
  "real_test_not_distinguishable_count": 10,
  "tie_forced_not_distinguishable_count": 9
}
```

Enforced in `run.py` in the `check_analytic_expectation` style, not only in tests:

- `distinguishable_count == resolved_count`
- `tie_forced_not_distinguishable_count` equals the count of zero gaps
- `real_test_not_distinguishable_count` equals the nonzero-gap count minus
  `distinguishable_count`, which is well defined because a tied pair has p exactly 1 and can
  never be distinguishable
- the three sum to `family_size`
- `resolved_count <= separable_count`, the D2.7 invariant, which `FamilyReport` already asserts
  and the headline check restates at the results boundary

The analytic proof still fixes `resolved_count` at zero here, so the committed values are 0, 10,
and 9; the formulas are the contract, the values are this data.

## 2. Module layout

`metrology/reporting.py` gains pure functions, no file IO, stdlib only so the D0.4 boundary holds:

| Function | Returns |
|---|---|
| `render_number(qualified_path, value)` | the one approved string for a corpus figure at that path |
| `findings_markdown(results, aggregates)` | the D1.6-ordered block |
| `findings_pair_rows(results)` | the compact five-column rows for the markdown table |
| `csv_pair_rows(results)` | the fully enumerated CSV rows of section 7 |

`render_number` takes the **source-qualified path**, `"results:pairs[].p_value"` or
`"aggregates:entries[].rank"`, matching the registry key exactly. The first draft took a bare
path while the registry was keyed by (file, path), an interface that contradicts its own
contract. No bare path collides across the two files at HEAD, so the ambiguity is latent rather
than active, which is precisely when it is cheapest to close: the first collision would otherwise
pick a renderer silently. Golden fixtures carry the qualified form,
`("results:pairs[].p_value", 0.4570207854105899, "0.457")`.

The markdown table and the CSV are **separate projections**, not one function serving both. The
first draft declared a single `pair_table_rows` feeding a six-column table and a CSV that was also
required to be a full flattening of each pair record; those two contracts are incompatible, since
the record carries far more fields than six. Each projection now declares its own column list and
each is tested against its own contract.

`experiments/swebench/report.py` does the IO. It reads `results/results.json` and
`derived/aggregates.json`, recomputes nothing, and offers two modes:

- `--check`: renders expected bytes and compares against what is on disk. Nonzero on any
  difference. This is the mode CI runs.
- `--write`: writes `results/pairs.csv` and splices the README block, each written atomically
  (temp file in the destination directory, then `os.replace`) so an interrupted run cannot leave a
  half-written result file that a later `--check` would compare against.

**Both modes run one shared `validate_sources(results, aggregates)` before any projection.** The
first draft assigned the cross-file checks to `--check` alone, which leaves `--write` able to
generate output from a reordered or inconsistent source and have the very next `--check` bless
what it produced. The validator covers the section 7 adjacency and name checks and the section 6
net-edge-against-aggregates agreement; on failure `--write` refuses to write anything at all, in
the `check_no_substitutions` spirit of halting before the work rather than after it.

`scripts/check_prose_numbers.py` implements the D1.8 membership check. It shares `render_number`
with the generator, deliberately: the accepted string set must equal the emittable one, and two
implementations of the same registry would drift. The first draft claimed the checker was
independent of the generator, which a shared renderer makes false. What actually guards against a
shared bug is a set of **golden formatting cases**: literal expected strings written by hand from
the section 3 table into the tests, in the source-qualified form above, so a defect in
`render_number` fails against constants no code produced.

## 3. The format registry, which is the checker's real contract

Generic rounding is rejected. The reason, confirmed against the committed corpus: at zero decimal
places `0.024`, `-0.022` and `0.072` all render as `0`, and `0.95` and `0.9006532462520331` both
render as `1`. Any corpus with floats would therefore make the bare integers `0` and `1` members
by accident, and those two appear throughout authored prose. The check would look strict and
enforce nothing.

Instead every numeric path in the corpus gets a declared renderer. The generator and the checker
both call `render_number`, so the set of strings the checker accepts is exactly the set the
generator can emit. There is no tolerance parameter anywhere.

The corpus at current HEAD has **59 numeric paths**: 7 in `aggregates.json` and 52 in
`results.json`, keyed by (file, path) with `[]` standing for any list index. The first draft said
52, which was the results file alone with the aggregates paths silently dropped, an error caught
in review by enumerating both files named in D3.2. The section 1 `primary.headline` addition
brings three more, so the count after the reopening is 62; the number that matters is not either
constant but the completeness property below, which is why the test derives the inventory rather
than pinning a count. A test regenerates the inventory from the two committed files and fails
if the registry does not cover it exactly, in both directions: an uncovered corpus path fails, and
a registry rule matching no corpus path fails, so the registry can neither lag the corpus nor
accumulate dead rules. Every path must match a rule or the checker fails loudly rather than
defaulting:

| Path class | Renderer | Example in, example out |
|---|---|---|
| counts and sizes (`family_size`, `n_items`, `resolved`, `rank`, `rank_a`, `rank_b`, `n01`, `n10`, `n_discordant`, `net_edge`, `size`, `rejected`, `separable_count`, `resolved_count`, `dropped_instances`, `total_pairs_affected`, `no_generation`, `no_logs`, `entries_predating_the_fix`, and the three `primary.headline` counts from section 1) | integer, no separators | `500` to `"500"` |
| gap floors and gaps (`first_rejection_gap_floor`, `gap_floor`, `required_net_edge_at_observed`, `largest_observed_gap`) | integer | `10` to `"10"` |
| published percentages (`published_rate`) | one decimal place | `74.4` to `"74.4"` |
| rates and probabilities (`discordance_rate`, `rate_difference`, `bootstrap.low`, `bootstrap.high`, `bootstrap.estimate`) | three decimal places, fixed | `0.072` to `"0.072"`, `0.1` to `"0.100"` |
| p-values (`p_value`, `adjusted_p_value`) | three decimal places, fixed | `0.4570207854105899` to `"0.457"`, `1.0` to `"1.000"` |
| powers (`max_attainable_power`) | three decimal places, fixed | `0.9999999999511919` to `"1.000"` |
| thresholds (`first_critical`, `alpha`, `bootstrap_level`, `bootstrap.level`, `target_power`) | six significant digits, trailing zeros trimmed | `0.002631578947368421` to `"0.00263158"`, `0.05` to `"0.05"` |
| instance counts from the MDE (`instances`) | one decimal place, fixed | `17.384765625` to `"17.4"` |
| seeds and resample counts (`master_seed`, `seed`, `n_resamples`, `bootstrap_resamples`) | integer | `20260727` to `"20260727"` |

**Fixed decimals everywhere except the threshold class, and that exception is bounded.** Trimming
trailing zeros is what would reintroduce the collision the registry exists to prevent: a p-value of
`1.0` trimmed becomes `"1"`, and a bootstrap estimate of `0.0` trimmed becomes `"0"`, which are
exactly the two bare integers that made generic rounding useless. So every float class renders at a
fixed width. Thresholds are the one class that trims, because six significant digits would
otherwise write `alpha` as `0.0500000`, and the class is safe to trim because none of its five
committed values is `0` or `1`.

The test that bounds this is scoped to **float classes only**: no float renderer may produce a bare
`"0"` or `"1"` for any committed corpus value. Integer classes must be allowed to, and that is not
a loophole but the finding: `separable_count` and `resolved_count` are both genuinely `0`, so prose
has to be able to write "0 of 19" and pass. Validated against the committed corpus while drafting
this section, which is how the wrong version of the assertion, one covering every class, was caught
before it reached code.

Two consequences to hold on to:

- **A percentage is a scaling, not a formatting.** Rendering `discordance_rate` as `7.2` percent is
  a different figure from `0.072`. If percent presentation is wanted at a path, it is a declared
  percent renderer at that path and the accepted string is `"7.2"`; there is no implicit
  multiplication anywhere, and a test asserts that no path accepts both its raw and its scaled
  rendering.
- **The registry is total.** A corpus path with no rule is an error, not a fallback, so adding a
  field to `results.json` in a later task forces a decision about how it may be written.

### Disclosed weakness

Integer membership is coarse. The corpus already contains most small integers, so a hand-typed
small integer in prose can pass by matching an unrelated path. The check's strength is on floats,
which is where fabricated figures actually look plausible, and on the drift check, which is exact.
Recording this rather than implying the membership check is airtight for integers.

## 4. What counts as a prose numeral

Scope, settled explicitly: **the entire README's running prose**, plus the markdown cells of the
notebook script, since PLAN.md section 2 names notebook prose alongside the README. Not only the
generated regions, because the hand-typed figure this check exists to catch would be written
outside them.

Tokenization runs in this order, and the order matters:

1. Fenced code blocks are removed and exempt.
2. Inline code spans are **not exempt as a class**. The first draft exempted any span containing
   an identifier, which turns `` `p=0.123` `` into a laundering channel, since the `p` is an
   identifier and the fabricated figure rides along. Instead, a span is exempt only when its
   **entire content** matches one bounded structural token, and the token classes that can carry
   arbitrary digits are **verified against the repository, not merely shaped**, because a
   grammar-only rule lets `` `docs/fake999.md` `` hide a `999` inside a plausible-looking path:

   - a file path, which must resolve to a git-tracked file (`git ls-files`), so a fabricated
     path fails and its digits get scanned;
   - a make target, which must appear in the Makefile's declared target list;
   - a leaderboard system name, which must equal an `entries[].system` value in
     `aggregates.json`;
   - a runner image label, from an explicit allowlist (`ubuntu-24.04`);
   - a dotted version string, a hex hash, and a task or decision ID, which stay grammar-bounded
     as in rule 3 because their grammars already exclude free digits: three dotted components, a
     required hex letter, a required `T`/`D` prefix.

   Any other span has rule 3's atomic-token stripping applied to its content and whatever
   numerals remain are membership-checked exactly like running prose, so `` `p=0.123` `` fails
   unless `0.123` is a corpus rendering. A span whose entire content is numeric stays **rejected
   outright** rather than scanned, so a genuine figure cannot be presented as code either.
3. Atomic tokens are removed before any numeral scanning, so their internal digits are never seen
   as figures: ISO dates, hex hashes, dotted version strings, URLs and link targets, and
   leaderboard system names of the `20251215_livesweagent_claude-opus-4-5` shape. Two of these
   patterns are bounded so ordinary numbers cannot masquerade as identifiers, verified against the
   corpus while drafting: a hex hash must contain **at least one letter a to f** in addition to
   being seven to forty hex characters, because the bootstrap seed `2026072700` is ten digits and
   matches the naive pattern; and a version string must have **at least three dot-separated
   components**, because two-component decimals are exactly the shape of `74.4` and every other
   published rate. No registry rendering contains two dots, so the three-component rule cannot
   swallow a result.
4. Markdown structure is removed: ordered-list markers at line start, heading markers, and table
   delimiter rows.
5. Label references absorb a following bare integer, because these are names rather than
   measurements: `Phase N`, `Experiment N`, `Layer N`, `section N`, `item N`, `T<n>.<n>`,
   `D<n>.<n>`. Restricted to bare integers, never decimals, so `Phase 0.072` cannot launder a rate.
   A test asserts every label pattern refuses a decimal. **`rank N` is deliberately not on this
   list**: a rank is a measured property of the analysed board, not a document name, and exempting
   it would let `rank 999` pass. Rank references are checked as ordinary numerals instead, which
   works because `aggregates.json` `entries[].rank` holds exactly 1 to 20, so a legitimate rank is
   a member and a fabricated one is not.
6. Whatever remains must render-match a corpus figure under section 3.

### Remediations this forces on the current README

Measured, not predicted. The current file has exactly four running-prose numerals: `Phase 0` on
line 10, and the ordinals `1`, `2`, `3` in the build-order table. `Phase 0` is covered by rule 5.
The table ordinals are standalone numerals in cells, and backticking them is not available because
rule 2 rejects bare numeric spans, so the `Order` column values are reworded to `first`, `second`
and `third`. `ubuntu-24.04` is already code-spanned and passes as a whole-token runner image
label; `Python 3.11.15` gains backticks and passes because rule 3's stripping removes the version
token from the span's content, leaving no numerals to check. Neither passes by a blanket span
exemption, because rule 2 no longer has one.

## 6. The pair table, and the option-1 trap in presentation

The table must not carry a per-pair floor column repeating `10`. D2.7 settled that the gateway
floor is the bar the family's **first** rejection must clear; a pair below it can still separate
after another pair opens the Holm sequence. A column of nineteen identical `10` values would
re-assert the superseded option-1 definition in a place no test looks. The gateway floor appears
once, in the lead.

Columns, every one a corpus read:

| Column | Source path |
|---|---|
| pair | `pairs[].name` |
| resolved-count gap | `pairs[].net_edge` |
| observed discordance | `pairs[].n_discordant` |
| observed p-value | `pairs[].p_value` |
| Holm-adjusted p-value | `pairs[].adjusted_p_value` |

One data-path subtlety the D4 scoping exposes: the gap column claims aggregate provenance while
its source, `pairs[].net_edge`, was computed by `run.py` from per-instance discordant counts. The
two coincide only because integrity gate 3 held. So the shared `validate_sources` of section 2
**validates every net edge against the adjacent resolved counts in `aggregates.json`**, alongside
the section 7 order validation, before either mode projects anything; a mismatch fails rather
than rendering a per-instance figure under an aggregate label. `findings_pair_rows` itself stays
a single-source projection of `results`.

The first draft had a sixth column, the per-pair minimum attainable p-value, computed at reporting
time by `p_value_floor(gap)`. That column is removed, for two reasons that compound. It violates
the no-recomputation contract the reporting layer states for itself. And its values fail the
design's own membership check, verified against the corpus: the registered gaps produce floors of
1, 0.5, 0.25 and 0.015625, of which 0.25 and 0.015625 appear in neither corpus file, while 0.5
would pass only by colliding with the unrelated MDE grid point `discordance_rate = 0.5`, which is
the accidental-membership failure in its purest form. The per-pair floor argument is carried by
the lead's gateway-floor-against-largest-gap inference instead; if a per-pair floor column is ever
wanted, the values must first be persisted into `results.json` by a recorded T3.2 reopening, not
computed in reporting.

A test still asserts the rendered table contains no column whose every value is the gateway floor.

## 7. CSV contract

`results/pairs.csv` is an exact row-wise projection of `results.json` `pairs`, not a bag of values.
The weaker invariant is rejected because it does not hold here: pairs 2 and 7 carry identical
`n01`, `n10`, `n_discordant`, `discordance_rate` and `p_value`, so a swap of their numeric payloads
would be invisible to a set-membership test.

The column list is enumerated here, not left as "the flattening", so the contract has no
interpretive slack. Twenty-four columns, one per field of the committed pair record, enumerated
from `results.json` rather than from memory (the first attempt at this list, written from memory,
invented an `mde_discordance_rate` field that does not exist and omitted `bootstrap_unit`, which
does):

```
name, system_a, system_b, n01, n10, n_discordant, net_edge, discordance_rate,
p_value, adjusted_p_value, verdict, separable,
bootstrap_low, bootstrap_high, bootstrap_estimate, bootstrap_level,
bootstrap_n_resamples, bootstrap_seed, bootstrap_unit,
mde_status, mde_rate_difference, mde_instances, mde_max_attainable_power,
required_net_edge_at_observed
```

Numerics render under their section 3 renderers, strings (`name`, `system_a`, `system_b`,
`verdict`, `mde_status`, `bootstrap_unit`) verbatim, booleans (`separable`) as lowercase
`true`/`false`. A test asserts the column list covers the pair record's flattened key set exactly,
in both directions, so a field added to the record in a later task fails here rather than being
silently dropped from the CSV.

The rest of the contract:

- Exact declared column order. Extra, missing or reordered columns fail.
- Exactly nineteen data rows plus one header row.
- Row *i* equals the deterministic flattening of `pairs[i]`, field by field.
- **Source order is validated against the other corpus file, never repaired.** Comparing the CSV
  to `pairs` in file order cannot detect a `results.json` whose pair list was itself reordered, so
  the check is cross-file: `pairs[i].system_a` and `pairs[i].system_b` must equal the systems at
  ranks *i+1* and *i+2* in `aggregates.json` entries order, and `pairs[i].name` must equal
  `rank_<i+1>_vs_<i+2>`. No sorting anywhere, because sorting would silently correct a reordering
  defect in `run.py` instead of reporting it. This validation lives in the shared
  `validate_sources` of section 2, so it guards both modes and the markdown table alike.
- Fixed float formats from the registry; quoting policy pinned to `csv.QUOTE_MINIMAL` with comma
  delimiter, which quotes nothing on this data since no field contains a comma, quote or newline,
  and a test asserts that expectation so a future field that would trigger quoting fails visibly
  instead of changing the byte format silently; `\n` line endings, trailing newline, no ambient
  state per D0.9 item 6.

## 8. README splice contract

Exactly one `<!-- findings:start -->` and one `<!-- findings:end -->`, in that order. The splicer
and the checker both fail on a missing marker, a duplicated marker, or markers in reverse order,
rather than splicing into the first pair found. Content between them is generated and
drift-checked byte-exact; content outside them is authored and membership-checked.

**Bootstrapping, stated because the current README has no markers while both modes reject their
absence:** the marker pair is inserted by hand exactly once, as part of this task's authored
Status rewrite, before the first `--write` runs. `--write` only ever replaces content between
existing markers; it never creates them, because a mode that inserts markers heuristically would
choose a location silently, and location is an authorship decision.

## 9. Notebook

`experiments/swebench/notebook.py`, a **notebook-compatible Python script** in percent-cell
format. It is not an `.ipynb` and adds no pinned dependency: no `nbformat`, no `jupytext`, so D0.5
requires no reproduce re-run. VS Code renders `# %%` cells natively and Jupyter opens it through
jupytext if a reader has it, neither of which this repo depends on.

Tests **execute it**, not merely import-scan it, because an import test proves the file parses and
nothing about whether it reads current results successfully. Execution asserts a clean exit and
that named figures it prints match the corpus.

"Reads rather than recomputes" is enforced by three mechanisms, because the first draft's ban on
three named imports proved nothing: it left inline arithmetic, scipy, and importing `run.py` all
open, and a bare module allowlist naming `metrology.reporting` would still expose
`build_family_report` and every other analysis-adjacent function in that module.

- **An imported-symbol allowlist, checked by `ast`.** The notebook's permitted imports are
  exactly the modules `json` and `pathlib`, plus the single symbol
  `from metrology.reporting import render_number`. Importing the module itself, or any other name
  from it, fails the test. Everything else, scipy included, is excluded by construction.
- **An explicit callable interface.** The notebook defines
  `main(results_path, aggregates_path)` and its `__main__` block only applies the default
  committed paths. Tests call `main` with sandbox paths directly; no monkeypatching, no chdir
  games, and the sandboxing cannot silently miss a hardcoded path because there is none outside
  the `__main__` block.
- **Sentinel flow coverage per output class, not one field.** A single p-value sentinel proves
  one read. Each of the six output classes gets its own planted sentinel in the sandboxed corpus,
  each chosen to render to a string no committed value renders to: a headline count, a pair
  statistic, a bootstrap bound, an MDE value, a grid value, a data-quality count, and one value
  inside each secondary. The execution test asserts every sentinel surfaces in the output, so
  every section is proven to flow from storage, not merely the one the test author picked.

### Required sections, which is where the registered outputs live

The notebook is not "some corpus figures". PREREG sections 2.1, 3, and 5 registered outputs that
currently exist only inside `results.json`, and each is assigned a home here so that "reported"
means rendered somewhere a reader will meet it. The notebook's required sections, each asserted
present by the execution test:

1. **The three-part headline** (PREREG 2.1), same fields as the findings block lead.
2. **The full nineteen-pair detail** (PREREG 5, tests 1 and 2): exactly 19 rows, each carrying
   the discordant counts, the paired bootstrap interval with its level, and the MDE at observed
   discordance with its status. This is where the per-pair intervals and MDEs registered as
   outputs are actually displayed; the README table stays compact per section 6, and the CSV
   carries the same figures for machine consumption.
3. **The declared MDE grid** (PREREG 5, test 4): exactly 6 rows, one per registered grid point,
   from `mde_grid`.
