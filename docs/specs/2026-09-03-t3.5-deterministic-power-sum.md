# T3.5 corrective design: the power sum becomes deterministic

Date: 2026-09-03
Revised: 2026-09-09
Status: approved by Jane on 2026-09-09. Implementation and canonical acceptance checks follow this design.
Task: PLAN.md T3.5, corrective. Narrow by construction.

Deliverable: remove BLAS kernel selection from `mcnemar_power`'s final reduction, then require
two green canonical executions of the corrected commit. One production reduction changes.

Binding prior decisions: D0.5 (nondeterminism is a bug to fix, not a caveat to write), D0.9 (the
canonical environment), D2.3 (one validator owns an invariant), D3.13 (**whose diagnosis and remedy
this corrects**).

## 1. What run 6 established

Run 33764897089 adopted the exact bytes run 33179082136 produced, and then failed to reproduce
them. The two runs recorded the same environment fields:

| | run 33179082136 | run 33764897089 |
|---|---|---|
| kernel | `Linux 6.17.0-1022-azure x86_64` | `Linux 6.17.0-1022-azure x86_64` |
| image | `Ubuntu 24.04.4 LTS` | `Ubuntu 24.04.4 LTS` |
| interpreter | `3.11.15` | `3.11.15` |
| numpy, scipy, pyarrow | `1.26.4`, `1.17.1`, `23.0.0` | `1.26.4`, `1.17.1`, `23.0.0` |

Seven distinct `max_attainable_power` transitions, every one 1 ULP, including
`0.9999990818191731` to `0.999999081819173`. Both values are below 1.0, so their difference
cannot be caused by the final clamp.

**The stored field varies within the declared canonical environment.** D3.13's macOS/Linux
explanation was one possible reading of the first comparison, not an isolated cause. The second
canonical run falsified the claim that adopting one Linux run's bytes would repair reproduction.
It does not rule out additional platform effects.

## 2. The local mechanism and the CI inference

Forcing OpenBLAS kernel selection through `OPENBLAS_CORETYPE` at one thread reproduces the
difference locally:

| kernel | probability hash prefix | contribution hash prefix | `np.dot` | `math.fsum` |
|---|---|---|---|---|
| Haswell | `85c0fd3e7e981a45` | `7d26f37af37204ef` | `0x1.ffffffffffff7p-1` | `0x1.ffffffffffff8p-1` |
| Nehalem | identical | identical | `0x1.ffffffffffff8p-1` | `0x1.ffffffffffff8p-1` |

Identical inputs, confirmed by hashing both arrays, produce different `np.dot` results under
different kernels while `math.fsum` is stable across both. This isolates a local mechanism.
[OpenBLAS documents `OPENBLAS_CORETYPE` as a kernel selector](https://github.com/OpenMathLib/OpenBLAS/blob/develop/USAGE.md).
Different Azure CPU models or OpenBLAS kernels are a plausible explanation for the CI drift,
but CI recorded neither. That attribution remains an inference.

**Thread pinning is not the fix, and this is why:** the probe already ran at one thread. The
variation is kernel selection, not reduction across threads, so `OPENBLAS_NUM_THREADS=1` constrains
something that was not varying.

## 3. The change

`metrology/power.py`, the final reduction of `mcnemar_power`, currently line 215:

```python
    return float(min(1.0, max(0.0, np.dot(d_probs, contribution))))
```

becomes

```python
    total = math.fsum(
        float(probability) * float(weight)
        for probability, weight in zip(d_probs, contribution, strict=True)
    )
    return float(min(1.0, max(0.0, total)))
```

`math` is already imported. No helper, no dependency, no environment variable, no Kahan
implementation, and no serialization change.

Three details carry weight:

- **`float()` on each operand.** Products use Python float multiplication rather than NumPy scalar
  operations. The observed defect is in the BLAS reduction; this does not establish a separate
  defect in NumPy scalar multiplication.
- **`strict=True`.** Both arrays are length `n + 1` by construction. If that ever stops being true,
  a length mismatch is loud rather than silently truncating the sum.
- **The clamp survives unchanged.** The comment above it already records why: summing about `n`
  float terms can overshoot 1 by an ulp, and an out-of-range probability would fail the
  `MdeResult` invariant downstream. That reasoning is unaffected.

`np.arange`, `binom.pmf`, `binom.cdf`, `binom.sf` and `_critical_counts` are untouched. This spec
does not claim they are deterministic on every platform. Run 6 exercised the old reduction;
canonical CI had not tested this change when the correction commit was prepared. Any remaining drift requires diagnosis before
close-out, not adoption of another sampled output.

## 4. What is deliberately not done

- **Quantizing the stored field.** Rejected in D3.13 and still rejected. `pow3` is a presentation
  rule; the T3.3 design maps a stored full-precision value to `"1.000"` and `run.py` stores the
  computed float unchanged. Collapsing storage into presentation would render values genuinely
  below one as a literal `1.0`.
- **A tolerance in the byte check.** "Byte-identical within an epsilon" is a weaker guarantee that
  would conceal the next real mismatch.
- **Pinning BLAS threads.** Shown insufficient in section 2 rather than argued against.
- **Adopting another run's bytes.** That is what D3.13 tried. There are no stable bytes to adopt
  until the computation is deterministic, which is the point of this spec.

## 5. The control

One behavioral test, at the registered corpus scale:

`n = 500`, `q = 0.106`, `delta = q`, `alpha = 0.05`, against a fixed-order `math.fsum` reference computed
independently in the test, compared with `==` rather than `math.isclose`. Exact equality is the
subject: a tolerance-based assertion would pass under exactly the defect this fixes.

At `delta = q`, every discordance goes one way. For each `d` in `range(n + 1)`, reject exactly
when `min(1.0, 2.0 / 2**d) <= alpha`. Sum the corresponding Python float probabilities from
`binom.pmf(range(n + 1), n, q)` with `math.fsum`, then apply the existing clamp. This reference
uses the exact two-sided test's rejection condition for a fully one-sided split, without copying
`_critical_counts` or the production contribution-array construction.

Measured before the change, on macOS at both the registered alpha and a Holm-corrected one:

| alpha | `np.dot` | fixed-order reference | apart |
|---|---|---|---|
| 0.05 | 0.999999999999999 | 0.9999999999999991 | 1 ULP |
| 0.0026315789473684212 | 0.9999999999999862 | 0.9999999999999863 | 1 ULP |

After approval on 2026-09-09, the added regression test failed under `np.dot` with
`0.999999999999999 != 0.9999999999999991` (exit 1), then passed after the reduction change
(exit 0). Some BLAS kernels already agree with the reference, so this test is not expected to
fail under every possible old-code environment.

It is one test, not a suite. `_critical_counts` is already covered, the clamp is already covered,
and the existing power tests already pin the values this function returns.

## 6. What this does not establish

**One green canonical run cannot show that a nondeterminism fix worked.** A single sample is
consistent with the defect still being present and simply not having fired. Two green runs of the
**same commit** are required, the second obtained with `gh run rerun`, because rerunning the same
SHA holds the committed inputs fixed while allowing another runner allocation. Different hardware
is possible, not guaranteed, and two passes are the required acceptance evidence, not proof of
determinism on every runner. A rerun retains its run ID and increments its attempt number, so
record both attempts and their verdicts. [GitHub's run identity reference](https://docs.github.com/en/actions/reference/workflows-and-actions/variables)
defines these identifiers.

Regenerate `results.json` and `cards.json` after the code change using `run.py` and
`report.py --write`, without `make reproduce` or another local fetch. Review every artifact diff;
only the two JSON files are expected to change. CI then tests whether those bytes reproduce.

This change removes the observed BLAS reduction mechanism. It does not promise bitwise identity
across every Python build: [Python's `math.fsum` documentation](https://docs.python.org/3.11/library/math.html#math.fsum)
notes possible double rounding on some builds. The canonical environment and byte gate remain
unchanged; a further mismatch is a finding to investigate.

## 7. Scope, measured rather than assumed

The reduction sites relevant to the scope review are:

| Site | Reduction | In the reproduce path | Observed across runs 5 and 6 |
|---|---|---|---|
| `power.py:215` | `np.dot` | yes | stored power fields differ; local probe isolates the reduction |
| `paired.py:201` | `differences.mean()` | yes, via `bootstrap.estimate` | stored field byte-identical |
| `paired.py:302` | `differences.mean()` | no, `clustered_bootstrap_difference` has no production caller | not exercised |
| `paired.py:293` | two `np.mean` calls | no, same function | not exercised |
| `paired.py:321` | `values[indices].mean(axis=1)` | yes, via bootstrap bounds | stored fields byte-identical |

The prior inventory omitted `paired.py:321` and misattributed `bootstrap.low` to the estimate
mean. The bootstrap means use NumPy's reduction path rather than the `np.dot` BLAS path isolated
by the local probe. Their stored outputs were byte-identical in the two CI comparisons, so the
evidence does not justify changing them in this repair.

That is not a proof that `np.mean` cannot vary; it is the observation that it did not, twice, on
the path this repair concerns. If a future run shows drift in a bootstrap field, it is a separate
finding with a separate entry, not a reason to widen this change now.

The T8.4 multi-experiment reproduce target is unaffected.
