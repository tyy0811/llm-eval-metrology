### `fetch_date` gets a committed source, by offline schema migration

`CANONICAL_FETCH_DATE = "2026-07-29"` is a literal in `run.py`, and the manifest carries no date
field: confirmed by reading both. Validating the card against a second literal in `report.py`
would create the duplicate this check exists to catch.

**No network fetch.** A fetch run today cannot establish the historical date `2026-07-29`; it can
only confirm that the pinned bytes are still reachable today. Re-fetching to obtain a date the
fetch cannot know would be ceremony that risks the committed digests for no evidence. This is a
schema migration performed offline:

1. Add `"fetch_date": "2026-07-29"` to `manifests/upstream_digests.json`.
2. **Prove the migration is additive**, as a one-time pre/post verification recorded in the task
   report: parse the manifest before and after, remove `fetch_date` from the after, and confirm
   the two are equal. This is not a permanent test, because a permanent one would have to reach
   into git history for the pre-migration bytes, and a suite that depends on history is a suite
   that breaks on a rewrite.
3. Delete `CANONICAL_FETCH_DATE` from `run.py`, with a test asserting the name is gone so the
   literal cannot return.
4. `run.py` and `validate_card_set` both read the date from the manifest.
5. Validate it as a canonical, real calendar date in `YYYY-MM-DD` form, parsed with
   `datetime.date.fromisoformat` and required to round-trip to the same string, so `2026-13-01`
   and `2026-7-29` both fail.

`fetch.py` gains `--fetch-date`, and its existing `--bootstrap` requires it, so a manifest can
never be created with an invented date. A normal run preserves the committed date rather than
stamping today's, which keeps the manifest free of ambient state per D0.9 item 6.

## 3. `validate_card_set`: total, declarative, structural

A declarative table maps every leaf of every card to exactly one rule. Enforcement is
bidirectional and structural, not a scalar-leaf walk: a walk alone lets an unknown empty object or
a nonscalar addition pass unseen.

**Structural requirements.** Exact top-level keys `{family, pairs}`. At every level, the object's
key set must equal the rule set's key set exactly, so an added key fails whether or not it holds a
scalar and an empty object or list fails unless a rule declares it. Lists are validated by exact
length with **indexed** rules. Exactly one rule matches each leaf; a leaf with no rule fails, a
rule whose card path does not exist fails, and two rules matching one path fail. Comparison is by
exact JSON type and value, never by tolerance and never by `==` alone, since `True == 1` and
`1 == 1.0` in Python.

**Four rule kinds.**

- **SOURCE**: equals the value at a named path in `results.json`, `aggregates.json`, or the
  manifest. `separability_basis` is a SOURCE rule against `results:primary.separability_basis`,
  verified equal in the committed pair, and not the prose rule the first draft made it.
- **CONSTANT**: equals an exact literal the engine registers (`TWO_SIDED_CONVENTION`, `RULE_HOLM`,
  `CARD_PAIR`, `CARD_FAMILY`, `"holm"`, `"adjacent_pairs"`), and exact literals for invariant
  prose: `claim_type`, `scope.comparisons`, `scope.excludes`, `definitions.separable`,
  `observed.note`, `limit.floor_label`, `limit.observed_extreme_label`.
- **PROSE_TEMPLATE**: for a generated sentence, a declared template of literal text plus
  source-qualified placeholders. The validator formats the template from sources and requires
  **exact string equality**, so both the wording and the figure are checked.
- **DERIVED**: equals a named pure function of sources. Used for the malformed-field disclosure
  text of section 4.

**Why PROSE_FIGURES is gone.** Measured against the committed card: of the nine prose fields the
first draft assigned to it, **eight contain no numerals at all** and only `limit.inference`
contains one. A numeral-only rule would have accepted arbitrary replacement prose in eight fields,
and in the ninth would have accepted a sentence whose conclusion was reversed while the numeral
stayed. That is not a weaker version of totality; it is an absence of it.

`limit.inference` is the one PROSE_TEMPLATE today. Its templates are declared per branch together
with the condition selecting the branch, and both the selection and the formatted string are
checked. The cost is that an engine wording change must be mirrored in the crosswalk, which is
the intent: a load-bearing inference sentence should not be rewordable without an explicit
decision.

**Lists.** `conditionality`, `disclosure.applies_to_headline`, `disclosure.applies_to_secondary`,
and `provenance.deviations` are validated by exact length, exact order, and exact values.
`applies_to_headline` must be empty, which is D1.11 at the card boundary.

**Indexed structural rules.** `ruler.split[0]` maps to the record's `n10` and `ruler.split[1]` to
`n01`, as two rules rather than one list-valued rule. The committed card reads `[36, 29]` against
`n01 = 29, n10 = 36`, so a reversed mapping would render the ruler's edge favouring the wrong
system with every individual number still correct.

### Coverage map

**The inventory is computed, not asserted.** No leaf count is pinned here, and the reason is
itself a measurement: the two pair cards do not have the same number of leaves, because their
deviation lists differ in length. A pinned count would be wrong for one of them today and wrong
for both the moment a disclosure is added. The computed inventory is the durable contract.
Checking revision 2's named rules against it found **six leaves with no rule**, so its "exactly
one rule per leaf" claim was not yet true:
`comparison.name`, `criterion.statistic`, `test.statistic`, `ruler.requirement_basis`,
`ruler.threshold_basis`, and `mde.alpha_basis`. Their rules:

- `comparison.name` is SOURCE against the matched record's `name`. The wrapper's key equality
  from the section below stays a **structural** guard and is not a second rule for this leaf, so
  the one-rule-per-leaf invariant holds.
- `criterion.statistic` and `test.statistic` share **one** registered statistic constant, so the
  family card and a pair card cannot name different statistics for the same procedure.
- `ruler.requirement_basis`, `ruler.threshold_basis`, and `mde.alpha_basis` are exact CONSTANT
  rules. These three carry the load D1.7 and D2.6 put on them, naming which threshold a number was
  computed at, so each gets a mutation control: a card that swapped
  `mde.alpha_basis` for the family-correction wording would be numerically correct and still lie
  about which alpha produced its MDE.

The totality test regenerates this inventory from the committed cards at test time rather than
pinning a count, in both directions, exactly as the number-format registry does.

Family SOURCE rules resolve against `primary`, `configuration`, and `secondary.non_tied_family`:
`headline.separable_count`, `headline.family_size`, `observed.resolved_count`, `criterion.alpha`,

leaf beneath all eleven.

Each pair card resolves against the `pairs[]` record whose `name` equals its `comparison.name`:
`system_a`, `system_b`, `test.p_value`, `test.adjusted_p_value`, `verdict`,
`ruler.observed_disagreements` against `n_discordant`, `ruler.observed_net_edge` against
`net_edge`, `ruler.required_net_edge_at_observed`, `mde.discordance_rate`, and every `mde` field

## 4. Provenance, exactly

### 4a. The manifest population, validated before anything is derived from it

Revision 2 derived provenance from the manifest without checking that the manifest describes the
analysed board. A manifest holding only the four systems named on the two illustrative cards would
have satisfied every revision rule while the family card described a twenty-system analysis. So
the population is validated first, and every requirement below holds on the committed manifest
today, measured while writing this section:

- Artifact systems equal the aggregate entries in **membership, uniqueness, and published order**,
  not as a set. Confirmed: the 20 artifact systems equal the rank-ordered aggregate systems
  exactly, with no duplicates.
- Each artifact appears exactly once.
- Each artifact URL's system component agrees with that record's `system` field. Confirmed: no
  artifact's URL disagrees with its own system.
- `board.url` embeds the same revision as `board.commit`. Confirmed equal at
  `7c4289f30aa1a1c63c2e2a25aae30c16d92b5114`.
- All artifact URLs share the expected repository and a single revision. Confirmed: one repository
  (`SWE-bench/experiments`) and one revision across all 20.
- The `source` and `secondary_source` labels are **derived from those repository identities**
  rather than compared against literals, so a card naming a repository the manifest never fetched
  fails. Confirmed derivable: the artifact repository is the artifact source and the board
  repository (`SWE-bench/swe-bench.github.io`) is the board source.
- `fetch_date` is a valid canonical calendar date per section 2.

Controls: an artifact missing, extra, duplicated, or reordered against the aggregates; an artifact
URL whose system component disagrees with its `system`; a `board.url` whose embedded revision
disagrees with `board.commit`; an artifact URL on an unexpected repository.

### 4b. The card provenance rules

- Exact `source`, `secondary_source`, `secondary_revision`, and `fetch_date` on every card, with
  `fetch_date` read from the manifest per section 2.
- `deviations` validated as an exact list: no missing, extra, reordered, or duplicate entry.
- **One artifact revision.** Every `artifacts[].url` must resolve to a single revision before that
  revision may be used as the family card's `secondary_revision`. All 20 currently agree; a mixed
  manifest must fail rather than silently taking the first.
- Each pair card's `pinned_revision` must agree with the manifest records for **both** of its
  systems, not one.
- The family card's `pinned_revision` equals `board.commit`; pair cards carry
  `secondary_source` and `secondary_revision` as null.
- **Malformed-field disclosures are derived, not matched loosely.** For each selected pair, the
  expected disclosure set is computed from that pair's aggregate entries: an entry whose
  `checked_is_malformed` is true contributes a disclosure naming its rank and quoting
  `checked_raw` exactly. A pair whose entries carry no malformed field must carry no such
  disclosure. This is what makes the D8 obligation checkable in both directions rather than a
  substring search for the word `checked`.

2. Jane approves it.

4. Implement `render_pair_table` and its snapshots against the approved reference.

**Status under revision 4.** Steps 1 to 3 are done: `fixtures/table_reference.html` is committed at
`c5d01d7` and approved as the reference for this component. Step 4 has not started, and does not
start until section 12's full-page reference is approved too, because D1.3 binds the **document**
hierarchy exactly as it binds a component: a renderer written against a component reference alone
would let the finished page's structure be whatever `report.py` happened to assemble. The
component approval is necessary and no longer sufficient.

Two things the component reference established that the renderer must carry, both departures from
this spec's earlier text: `render_pair_table` emits a `div.pair-table-block` wrapper around the
scroll container and the disclosure note, because `render_document` joins fragments into a flex
column with a 1.75rem gap that would otherwise strand the note away from its table; and the scroll
container carries `tabindex="0"`, `role="region"`, and an `aria-label`, because Safari does not
focus scroll containers automatically.

```python
render_pair_table(columns, rows, *, heading, disclosure) -> str
```

Emits semantic `table`, `thead`, `tbody`, and a `caption` carrying the heading, inside a container
with horizontal overflow so a narrow screen scrolls the table rather than the page. Escapes every
heading, disclosure, header, and cell through `html.escape`. Rejects duplicate column names and
any row whose width differs from the column count.

Rows come from `reporting.findings_pair_rows`, already rendered. The README markdown table and the
card HTML table are two renderings of **one** projection, so the surfaces cannot disagree about a
pair. The disclosure states that D4 qualifies the observed-discordance and p-value columns, while
pair identity and the resolved-count gap derive from published aggregates.

## 10. The plain-language finding layer

### 10.1 It is engine-emitted, so the crosswalk covers it

The finding layer's copy carries figures, and D3.5 requires every prose figure to render through
`render_number` at a source-qualified path while section 3's crosswalk is total over `cards.json`.
A presentation-layer implementation in `report.py` would satisfy the first and forfeit the second,
leaving the most-read sentence in the document as the one part with weaker guarantees than the
table beneath it. So `family_card_json` emits a `plain_language` block and `validate_card_set`
maps every one of its leaves, exactly as for every other leaf.

This is the only engine change revision 4 requires. No statistic changes, and no change to any
existing field.

### 10.2 The block, and every figure's source

Measured against the committed corpus while writing this section: every figure the contract needs
already exists as a registered, source-qualified path, so the layer rewords validated leaves
rather than inventing quantities.

| Leaf | Kind | Source or rule |
|---|---|---|
| `plain_language.lead` | PROSE_TEMPLATE | `{board_size}` from `aggregates:family_size` |
| `plain_language.lead_basis` | CONSTANT | names `distinguishable_count`, the observed test |
| `plain_language.headline.count` | SOURCE | `results:primary.headline.distinguishable_count` |
| `plain_language.headline.of` | SOURCE | `results:primary.family_size` |
| `plain_language.headline.unit` | CONSTANT | `neighboring pairs` |
| `plain_language.scope` | PROSE_TEMPLATE | `{board_size}`, `{family_size}`, `{n_items}` |
| `plain_language.comparison.largest_lead` | SOURCE | `results:primary.largest_observed_gap` |
| `plain_language.comparison.opening_lead` | SOURCE | `results:primary.first_rejection_gap_floor` |
| `plain_language.comparison.unit` | CONSTANT | `tasks` |
| `plain_language.comparison.largest_lead_label` | CONSTANT | `largest lead` |
| `plain_language.comparison.opening_lead_label` | CONSTANT | `minimum opening lead` |
| `plain_language.analogy` | PROSE_TEMPLATE | `{opening_lead}`, `{largest_lead}` |
| `plain_language.task_level_note` | PROSE_TEMPLATE | `{largest_lead}`, `{opening_lead}`, gated on the premise below |
| `plain_language.task_level_basis` | CONSTANT | names the aggregate-derived basis |
| `plain_language.non_claims[0..1]` | CONSTANT | one rule per index |

**`family_size` is two different numbers under one name, and the collision is load-bearing.**
`aggregates:family_size` is **20**, the systems on the board. `results:primary.family_size` is
**19**, the adjacent pairs among them. The lead sentence needs 20 and the headline needs 19. A
swapped pair of sources renders "no neighboring top-19 pair" or "0 of 20" with every number still
individually correct and every type still matching. Section 13 gives this its own control.

**The analogy must not overclaim.** Clearing the opening lead is **necessary, not sufficient**: a
gap of 10 is the smallest at which a rejection is reachable at all, at best-case discordance. The
analogy therefore says a pair had to reach the mark before a reliable difference was even
possible, never that reaching it would have demonstrated one.

**The scope sentence supplies the relationship the figures alone do not.** A nontechnical reader
meeting 20, 19, and 500 separately has no way to connect them, so the layer states it: the top 20
creates 19 neighboring comparisons, each measured on 500 tasks. Its three placeholders are
`aggregates:family_size`, `results:primary.family_size`, and `aggregates:n_items`, which means
this one sentence exercises the collision above in both directions and is where a swap shows up
most legibly.

**The task-level note is gated on its premise, not only on its figures.** `results:primary.note`
already carries the technical statement, that the count follows from published resolve rates alone
and the per-instance work cannot overturn it, and `results:primary.needs_per_instance_data` is
`false`. The plain sentence is a second template, not a paraphrase checked by substring: the
maximum attainable significance for a pair is bounded by its lead, so task-by-task detail moves a
pair's p-value only within that bound, and a lead of 7 cannot reach the bar even when every
disagreement runs one way.

That claim is **conditional**, and the condition is a fact about this run rather than a general
truth. So the rule requires `results:primary.needs_per_instance_data` to be `false` before the
template may be emitted at all, and `plain_language.task_level_basis` states the
aggregate-derived basis in words. A run where per-instance data *is* needed must not carry this
sentence, and the validator must refuse a card that carries it anyway. Without the gate the rule
would check only the 7 and the 10, and would happily certify the sentence on a run whose headline
did depend on per-instance work. Section 13 controls exactly that: flip the premise, keep the
figures.

### 10.3 Crosswalk coverage

Section 3's rules apply unchanged in kind. Totality extends automatically, because the leaf walk
is structural and a new block with no rules would fail as unmapped rather than pass unnoticed.
`non_claims` is validated by exact length, order, and value, one indexed rule per element, as
`conditionality` already is.

### 10.4 The construction and rendering boundary

`family_card_json(report: FamilyReport) -> dict` receives only a `FamilyReport`, confirmed by
reading it. A `FamilyReport` does not carry the board size, the task count, or
`primary.headline.distinguishable_count`. So the block cannot be built inside `family_card_json`
without either deriving those quantities or reaching outside its input, and the nearest available
substitute, `report.resolved_count`, is numerically equal today and is exactly the substitution
D3.4 forbids. The boundary is therefore explicit:

```python
@dataclass(frozen=True)
class PlainLanguageInputs:
    board_size: int              # aggregates:family_size
    family_size: int             # results:primary.family_size
    n_items: int                 # aggregates:n_items
    distinguishable_count: int   # results:primary.headline.distinguishable_count
    largest_lead: int            # results:primary.largest_observed_gap
    opening_lead: int            # results:primary.first_rejection_gap_floor
    needs_per_instance_data: bool  # results:primary.needs_per_instance_data

def plain_language_finding(inputs: PlainLanguageInputs) -> dict: ...
def render_plain_language_finding(block: dict) -> str: ...   # in metrology.cards
```

- `run.py` populates `PlainLanguageInputs` from the registered paths, and is the only place that
  reads them. Every field is required; there is no default and no fallback, so a missing source
  is a `TypeError` at construction rather than a plausible substitution at render time.
- `plain_language_finding` is pure: same inputs, same block, no file access and no ambient state.
- `family_card_json(report, *, plain_language)` accepts the **completed block** and embeds it. It
  neither builds it nor reads a file, so the D3.4 substitution has nowhere to happen.
- `render_plain_language_finding` lives in `metrology.cards`, keeping HTML ownership inside the
  card module as section 2 requires.

**One table drives both the rule and the rendering.** The leaf-to-path mapping of section 10.2 is
a single module-level constant. `validate_card_set` builds its SOURCE and PROSE_TEMPLATE rules
from it, and `render_plain_language_finding` calls `render_number` with the same declared paths
for every figure it prints. Two copies of that mapping would let the validated path and the
rendered path drift while both stayed individually correct, which is the shape D1.12 exists to
prevent and which section 13 controls.

`render_plain_language_finding` prints **no** figure except through `render_number` at its
declared path, per D3.5.

## 11. The document hierarchy

### 11.1 Order, and the collapsed technical apparatus

1. **The finding layer.** Lead sentence, the `0 of 19` figure, the scope sentence, the
   lead-versus-mark comparison, the analogy, the task-level note, and the non-claims.
2. **The technical apparatus, collapsed**, holding everything else:

```html
<details class="technical-apparatus">
  <summary>Show statistical details and audit trail</summary>
  ...family card, nineteen-row table, two D8 pair cards...
</details>
```

Inside it, in order: the **family card** unchanged in structure from the existing
`render_family_card`; the **nineteen-row table**, all nineteen rows, from `findings_pair_rows`;
and the **two D8 pair cards** in `illustrative_pair_names` order.

**A divider is not progressive disclosure.** An earlier draft of this section proposed one, and it
fails the contract: a divider leaves the duplicate headline, the p-values, the system identifiers,
and the provenance immediately visible, which is precisely what section 1.1 item 6 moves out of
the first reading. The `details` wrapper is what makes the plain-language layer's first reading
uncontested, and it does so while leaving `render_family_card`, `render_pair_card`, and their
approved snapshots untouched. It is closed by default and interactive.

**Two quantities, three rendered occurrences.** Measured against the current renderer, not
inferred: `metrology/cards/__init__.py:287` renders `separable_count` of `family_size` as the
family banner, and `:307` renders `resolved_count` of `family_size` as "Resolved by the observed
test". The finding layer adds a third occurrence, of the observed count again. So the document
carries `0 of 19` three times across two distinct quantities, and on this data every one of them
is the same three characters. No value check can separate them; only the labels can.

All three labels are guarded. The finding layer names the observed test, the family banner keeps
its existing separability wording, and the family card's observed line keeps its existing wording.
Section 13 controls all three. Collapsing the apparatus means only the plain-language occurrence
is visible on first reading, which removes the reader-facing ambiguity even though the guard
against a label swap remains necessary for the other two.

### 11.2 Human labels, and the conversion that does not exist yet

**Measured, not assumed:** `render_pair_card` currently does `label = escape(comparison["name"])`
and renders the heading "Pair verdict: rank_3_vs_4". The "rank 3 against rank 4" wording in
`fixtures/verdict_reference.html` was aspirational fixture prose that no renderer ever emitted, so
the conversion the contract asks for has to be built, not merely wired up.

```python
def pair_display_label(name: str) -> str: ...   # "rank_3_vs_4" -> "Ranks 3 and 4"
```

Pure, in `reporting`, total over the `rank_{a}_vs_{b}` shape that
`illustrative_pair_names` produces, and raising on anything else rather than degrading to the raw
string, because a silent passthrough would reintroduce the identifier it exists to remove.

**Where it applies, and where it deliberately does not.**

- **Applies:** the pair card heading. This changes `render_pair_card` output and therefore the two
  approved snapshots `snapshot_pair_gap0.html` and `snapshot_pair_gap7.html`, which are
  regenerated and reviewed against the diff rather than blessed.
- **Does not apply:** the nineteen-row table's `pair` column. Those cells come from
  `findings_pair_rows`, which is the single projection shared with the README markdown table
  (section 5). Relabelling there would rewrite the README block, break `report-check`, and split
  the one projection that exists to keep the two surfaces from disagreeing. The table is technical
  apparatus and its raw names are correct there.
- **Does not apply:** `comparison.name` in `cards.json`, which stays the machine identifier the
  crosswalk keys on.

The long submission identifiers, the p-values, the Holm terminology, the provenance seal, and the
deviations all sit in progressive disclosure, which the pair card already implements with
`details` and `summary`.

### 11.3 What progressive disclosure means here

The finding layer states no p-value, names no system, uses the word Holm nowhere, and shows no
provenance. A reader who stops after it has a correct and complete headline. Everything the
contract lists as technical detail is reachable in one interaction from the same page.

### 11.4 `TABLE_HEADING` and `TABLE_DISCLOSURE`, reconciled

Revision 3's plan proposed values that predate the approved component reference. The reference
governs, so:

- `TABLE_HEADING = "Every adjacent pair, as tested"`, the approved caption. The longer alternative
  is not adopted: the caption box is as wide as the table rather than as wide as the scroll
  container, so at a 320px viewport a longer caption is only partly visible until the reader
  scrolls sideways, and the approved wording clears that edge.
- `TABLE_DISCLOSURE` is the approved note text from `table_reference.html`, verbatim, including
  "both p-value columns", which matches the sentence already committed in `metrology/reporting.py`
  and correctly extends D4 to the Holm-adjusted column.

A test asserts the rendered document's caption and note equal the reference's, so the two surfaces
cannot drift.

## 12. The full-page reference, and the second D1.3 gate

`metrology/cards/fixtures/page_reference.html`: one standalone page, inlining the current
stylesheet, showing the whole hierarchy of section 11 with clearly labelled illustrative figures,
in the fixture convention already established. It carries the finding layer, then
`details.technical-apparatus` holding a family card, a table reduced to a handful of rows **with a
visible statement that the shipped table carries all nineteen**, and one pair card headed by
`pair_display_label`.

**The apparatus is closed by default and left interactive**, so the reviewer sees exactly what a
first-time reader sees and can then open it. A reference that shipped the apparatus open would
approve a hierarchy nobody will encounter, which is the same failure as approving a renderer's own
output. The `details` element is not stubbed, disabled, or forced open for screenshot purposes.

### 12.1 This reference carries real figures, and that is a departure

Every prior fixture uses invented numbers, and T2.6 makes fixtures the one sanctioned home for
illustrative figures. This one inverts that, for a reason specific to what it is for: the artifact
under approval is **public copy**, and copy cannot be judged against invented quantities. "No
neighboring top-1111 pair showed a reliable difference" tells a reviewer nothing about whether the
sentence works, and the qualifying-mark analogy collapses entirely when the mark and the lead are
arbitrary. A layout reference can be illustrative; a copy reference cannot.

So the finding layer renders the committed Experiment 1 figures: 0 of 19, a top 20, 500 tasks, a
largest lead of 7 against a minimum opening lead of 10.

Two consequences, both handled rather than accepted:

- **The stamp inverts.** It states that the figures are the committed values and that the page is
  a layout and copy reference rather than a published result. It must not claim the numbers are
  invented, which would be false, and it must not read as a result artifact, which `cards.html`
  will be.
- **Staleness is guarded, not hoped for.** A fixture holding real figures goes stale silently,
  which is the exact failure `verdict_reference.html` already demonstrates for its stylesheet. A
  test asserts every figure in the reference equals the committed corpus value at its declared
  source-qualified path, so the reference cannot drift from the data it quotes.

The technical apparatus inside it still shows a reduced table, and that reduction stays clearly
labelled per section 1.2. Reduced row count is a layout convenience; altered figures would be a
copy defect.

It is committed and approved **before** any renderer for the finding layer exists, and before
`render_pair_table` is implemented. D1.3's reasoning binds the document exactly as it binds a
component: a hierarchy assembled by `report.py` first would make the page's structure whatever the
assembly happened to produce, and the fixture would then record that as the baseline.

The reduced row count in the reference is a fixture convenience and establishes nothing about
production, per section 1.2. The reference must say so on its face.

## 13. Additional negative controls for revision 4

Each shown red before its guard exists.

- **The `family_size` collision.** Swap the two sources so the lead reads "top-19" and the
  headline reads "0 of 20". Both templates must fail. This is the control the whole of section
  10.2's warning exists for, and neither figure is individually wrong.
- **The three `0 of 19` occurrences.** Render the finding layer with the family banner's
  separability wording; render the family banner with the observed wording; render the family
  card's observed line with the separability wording. All three must fail on their labels, since
  none fails on its value.
- **The premise flipped, the figures kept.** Build the block from inputs with
  `needs_per_instance_data` true while `largest_lead` stays 7 and `opening_lead` stays 10. The
  task-level note must be refused. This is the control that separates a gated rule from one that
  checks only numerals, and without it the sentence would certify a run whose headline did depend
  on per-instance work.
- **The leaf-to-path mapping drifting.** Point the renderer's path for one figure at a different
  registered path while the validator keeps the original. Both the rendered figure and the
  validated value stay individually correct, so the control asserts the two read the same constant
  rather than comparing outputs.
- **`family_card_json` substituting `resolved_count`.** Construct a card whose headline count came
  from `report.resolved_count` rather than `primary.headline.distinguishable_count`. Equal values,
  so this must fail on the source path, and it is the concrete form of the D3.4 substitution the
  boundary of section 10.4 exists to prevent.
- **`pair_display_label` degrading.** Feed it a name outside the `rank_{a}_vs_{b}` shape and
  require it to raise rather than return the input. A passthrough would put the raw identifier
  back into the heading with no test failing.
- **The apparatus shipped open.** Assert the rendered document's `details.technical-apparatus`
  carries no `open` attribute, and that the family card, the table, and both pair cards are inside
  it rather than siblings of it. A document that renders every component correctly but leaves them
  all immediately visible satisfies every other control here and still fails the contract.
- **The table reduced in production.** Distinct from the post-hoc selection control below: assert
  the shipped document's table parses to nineteen data rows even though the reference shows fewer,
  so the fixture's convenience cannot leak into the renderer.
- **`distinguishable_count` swapped for `separable_count`** in the headline rule. Must fail on the
  source path even though the values are equal, which is why the rule names a path rather than
  comparing numbers.
- **The analogy overclaiming.** An analogy asserting that reaching the mark would have shown a
  difference must fail against the declared template.
- **The task-level note reversed**, claiming per-instance data could overturn the headline while
  retaining its numerals. The numeral-only failure mode of the first draft's `PROSE_FIGURES` is
  the reason this is a template and not a figure check.
- **A non-claim dropped, added, or reordered.** Exact list validation.
- **A post-hoc pair selection.** A rendered document whose table carries fewer than nineteen rows,
  or whose pair cards are not exactly `illustrative_pair_names`, must fail. This is section 1.2's
  guard, and it is the one control that exists because of a layout exploration rather than a
  defect.
- **A system identifier or a p-value in the finding layer.** The first reading must contain
  neither; assert against the rendered finding fragment, not the whole page.
